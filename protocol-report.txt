GROHE Sensia Arena: Bluetooth protocol and device control
Static reverse-engineering report, 2026-10-16

RESULT

The normal remote-control entry point uses BLE. The phone is the advertising
peripheral/GATT server; the toilet is the connecting central. Commands travel
as phone notifications and status arrives as writes from the toilet. A controller
that only scans for a toilet and connects as a BLE central will not reproduce
this app's role.

The app's handshake, outgoing frame builder, operation codes, custom setting
encoders, and incoming status parser are recovered. This is an app-derived
protocol specification, not a hardware-validated implementation.

2. APP-LEVEL HANDSHAKE

All byte offsets in this report are zero-based. Treat byte values as unsigned
unless explicitly reproducing Java signed-byte behavior.

The first accepted connection sets state 1 (connecting). For an incoming
packet p, (p[19] & 0xF0) == 0 identifies a pairing request. The app copies
p[3..8] into six identity fields named MAC address. If p[9] == 1 it remains
connecting and sends opcode 00. Otherwise it sets state 2 (connected), sends
opcode 00, and marks custom settings sent.

An initial non-pairing status can also complete connection: save the identity
to local history, enter state 2, and send opcode 00. Outgoing wire bytes
13..18 echo the received identity, and byte 19 encodes phase 1 or 2.

No PIN, challenge-response or application encryption appears in this inspected
BLE handshake. That does not establish the toilet firmware's admission policy
or all Bluetooth link security. The normal physical pairing procedure still
needs to be followed and observed on the actual model.

Sources: BLEManager.java:283, 953, 990, 994; toilet/NToiletConnectionManager.java:118,144.
The SQLite T_ToiletInfo table stores names and identity/MAC history, not a
cryptographic credential in these methods.

3. PHONE-TO-TOILET FRAME

Exactly 20 bytes are notified. A 19-byte common payload is prepended with 00:

  wire[0]       00
  wire[1]       operation code
  wire[2]       custom strength, temperature, width
  wire[3]       custom massage/position, plus bit 7 status/drainage flag
  wire[4]       common settings and connected/connecting flag
  wire[5..7]    packed local date/time
  wire[8..11]   optional schedule fields
  wire[10]      bit 6 is always set, even with no schedule
  wire[12]      zero in the common builder
  wire[13..18]  six identity bytes from handshake
  wire[19]      1 connecting, 2 connected; other state behavior in source

wire[4]: bits 7..6 auto-wash delay; bit 5 seat-heater-off; bits 4..2 encoded
seat temperature; bit 1 auto-wash enabled; bit 0 set in states 1 and 2.
Seat-temperature UI indexes 1..5 map to 1,3,5,6,7 before shifting left 2;
other indexes map to zero.

Date/time, truncate each result to one byte:
  wire[5] = (month_zero_based << 4) | ((day_of_month - 1) >> 1)
  wire[6] = ((day_of_month - 1) << 7) | (hour << 2) | (minute >> 4)
  wire[7] = minute << 4

wire[3] bit 7 is state-dependent: with REQ_TOILET_STATUS true, it is the
inverse of auto-drainage mode and the request flag is consumed; otherwise
it is set when auto-drainage mode is active.

Schedule fields are generated only when isTimeSettingSendding is true.
They encode power-saving/room-refresh choice, repeat, relative start time,
and duration. The recovered builder is retained at BLEManager.java:613-687;
its minute rounding and relative-time arithmetic need capture validation.

sendMessage(byte[]) ORs at most three supplied bytes into payload offsets
0..2 (wire 1..3). There is no app checksum added in the send path.
Commands cannot be implemented as isolated one-byte writes. Preserve the
current settings and identity when building even a stop or lid command.
Sources: BLEManager.java:494, 562, 576, 709.

The parser also interprets p[5] bits 1/2/0 as descaling/error/recommendation.
This overlaps counter parsing; model-specific interpretation needs validation.
Its model constants name 0 Emerald, 1 Citrine, 2 Arena Wall, 3 Arena Floor;
additional generation constants exist, but this does not identify the user's
physical model. Source: NToiletInfoManager.java:9-19.

Status changes notify UI listeners for seat occupancy, shower stop, dryer stop,
and descaling. Firmware enforcement of occupancy interlocks is not established
by these UI transitions.

6. BUNDLED CLASSIC PATH

ClassicBluetoothManager uses Android bonding and insecure RFCOMM socket API
with SPP UUID 00001101-0000-1000-8000-00805F9B34FB. Discovery UI filters names
containing "Shower toilet". Connect retries up to three times with one-second
delays. No application PIN is supplied in the inspected pairing path.

Outgoing frames are 7 bytes: opcode, two custom bytes, settings byte, three
date/time bytes. Settings are included in every command. The first socket
read triggers opcode 00. Incoming reads must be exactly 22 bytes to be parsed;
there is no stream reassembly visible in that receiver.

Most operation codes match BLE. Mild wash indexes 0..5 instead map to
8E 9E AE BE CE EE. Do not merge the two mappings.
Sources: bluetooth/ClassicBluetoothManager.java:32,434,479,493,529,707,733,768,841;
activity/B001Activity.java:158,290; toilet/ToiletInfoManager.java:446.

7. WHAT REMAINS UNRESOLVED

Confirmed statically: app identity, active BLE route, GATT role/UUIDs,
app-level handshake, command framing, operation encoders and status decoding.
Partial: model-specific command semantics, schedule/counter behavior.
Unresolved: physical pairing admission, actual firmware support, radio timing,
notification subscription requirements, reconnect behavior and hardware results.

No periodic BLE heartbeat was found in focused manager/NT-activity inspection;
no measured packet cadence is available. This does not prove one is unnecessary.
Receive temperature shift >>3 differs from outgoing <<2. Counter arithmetic
includes suspicious signed-byte shifts. Keep these as observations, not a
corrected specification, until compared with captured packets.
The decompiled setUuid conditional contains a dubious nested ternary; its exact
branch structure should be checked against bytecode before a literal port.
The handshake accesses p[19] before checking length; a new implementation
should validate packet length before decoding it.

The next useful validation is a Bluetooth HCI capture of normal pairing,
idle status, and one ordinary control action using the official app on the
user's own toilet. Compare identities, phase flags, settings and timing before
implementing a peripheral/server controller. Avoid blindly zeroing settings or
replaying toggle, reset, descaling or drainage commands.

No live toilet was connected, no command was transmitted, and no controller app
was built. No persistent REA configuration was changed for this investigation.
